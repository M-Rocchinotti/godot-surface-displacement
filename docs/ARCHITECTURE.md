# Architecture

How Surface Displacement works, and why it is built this way. The README covers use, measured
cost and limitations; [RESEARCH.md](RESEARCH.md) the engine facts the design rests on.

## 1. The problem and the three layers

Godot 4.7 material shaders have vertex, fragment and light stages only: no tessellation, no mesh
shaders, no virtualized geometry. So "surfaces with height maps look like real geometry" is built
from three layers that each do what the engine allows:

| Layer | Where | What it gives | Code |
|---|---|---|---|
| Parallax occlusion mapping (POM) | every SD material, any distance up to the fade | per-pixel relief at the height map's full resolution, occlusion between stones, shadows received on the relief (`LIGHT_VERTEX`), self-shadowing | `shaders/sd_core.gdshaderinc`, `sd_march.gdshaderinc`, `sd_surface.gdshaderinc` |
| Near-camera geometry | ground within 7.7 m of the camera (Epic) | real vertices displaced by the height map: silhouettes, real depth (SSAO, intersections), coarse relief | `nodes/displacement_field_3d.gd`, `shaders/sd_field.gdshaderinc` |
| Pebble scatter | gravel layers within ~8 m | loose stones as real little meshes | `nodes/pebble_scatter_3d.gd`, `shaders/sd_pebble*.gdshader` |

Plus an offline Blender tool (`tools/bake_displaced_mesh.py`, not shipped) for the few props whose
silhouette POM cannot give.

## 2. Conventions

- **Height** is the red channel, 1 = top, remapped by `height_remap` (x -> 0, y -> 1).
- **Relief in metres** along a *relief axis* `A`: `z = height_m * (h - height_center)`. `A` is the
  surface normal for UV mapping, world +Y for world-planar mapping, the projection axis (sign
  of the normal) for each triplanar plane. `height_center` is UE's "Displacement Center": 1 =
  relief below the surface (classic POM, walls), 0 = above it (ground under a field).
- **The march parameter is the relief height z**, not the ray distance. A view ray that hits the
  flat surface at `P` passes height `z` at `uv(z) = uv(P) + duv_dz * z` with
  `duv_dz = (gu.V, gv.V) * (N.A) / (N.V)`, where `gu`, `gv` are the gradients of u and v along
  the surface (1/m), `N` the surface normal and `V` the unit vector towards the camera. Moving
  `z` moves the ray point by `V * z * (N.A) / (N.V)`; that offset gives `LIGHT_VERTEX` and the
  optional depth. The same formula with `L` for `V` gives the self-shadow ray.
- The gradients come from the mapping: world-planar and triplanar ones are constant (the mapping
  is linear in the world position); for UV mapping they are the cotangent frame from
  screen-space derivatives of the position and the UVs (exact per triangle, no dependence on the
  mesh's tangent sign convention).
- Triplanar faces use a right-handed (image right, image up, outward axis) frame on every face, so
  normal maps read the same way on all six sides.

`tests/render_tests.gd` (`pom_matches_ray_traced_height_field`) checks all of this against a CPU
ray / height-field intersection written from these conventions, independently of the shader.

## 3. The surface shaders

```
variants/sd_<mapping>_<quality>[_depth].gdshader   (generated by tools/generate_variants.py)
  render_mode diffuse_burley, specular_schlick_ggx;
  #define SD_MAPPING_UV | SD_MAPPING_WORLD | SD_MAPPING_TRIPLANAR
  #define SD_POM, SD_SELF_SHADOW, SD_DEPTH_WRITE (as the name says)
  #include sd_surface.gdshaderinc   -> vertex(), fragment(), light()
      #include sd_core.gdshaderinc -> uniforms, mappings, self-shadow
          #include sd_common.gdshaderinc -> quality globals, fade, normal-map helper, Godot BRDF
          #include sd_march.gdshaderinc  -> the march (shared with the field)
```

Quality is switched by swapping a material's shader between the flat, POM and POM + self-shadow
variant of the same mapping (`SDMaterials.set_quality`); all variants share one set of uniforms,
so parameters survive. Depth write is a separate, opt-in axis that survives the swaps. The
numbers that differ between presets (steps, fade, LOD bias, self-shadow steps and softness) are
global shader uniforms, so they change without recompiling anything.

### 3.1 The march (`sd_march`)

1. **Level of detail first.** The mip level is computed once, from the rasterized uv's
   derivatives, before any divergent control flow (`sd_march_lod`); every sample inside the loop is
   `textureLod` at that level. Implicit derivatives inside a data-dependent loop are undefined,
   and a missing mip chain makes every sample read the full-size map (the crater bug the research
   found). If the level is at or above `sd_pom_range.w`, the relief is below a pixel and the march
   is skipped.
2. **Adaptive linear search** from the top of the relief slab `(1 - c) * amp` down to its bottom
   `-c * amp`, with `mix(max_steps, min_steps, N.V) * pom_steps_scale * fade` steps.
3. **Bisection** of the bracketing interval (`sd_pom_steps.z` steps), then a final **secant** (a
   linear interpolation of ray-minus-relief in the last bracket, no extra sample).
4. **Distance fade**: `amp *= 1 - smoothstep(fade_start, fade_end, distance)`, and the step count
   with it. Beyond the fade end the shader does no march at all: plain normal mapping.

Final texture samples use `textureGrad` with the rasterized uv's derivatives (the hit uv jumps at
stone edges). The flat UV and world variants use `texture()`; the flat UV variant then matches ORMMaterial3D
exactly (render test).

### 3.2 Lighting

- `LIGHT_VERTEX = VERTEX + offset`: the engine substitutes it for the fragment position after the
  user fragment code, so shadow-map lookups and light falloff happen at the relief hit.
- **Self-shadowing** needs the light direction per light, which only `light()` has, and a custom
  `light()` replaces the engine's direct lighting. `sd_brdf` therefore repeats Godot 4.7.2's
  `light_compute()` for its default modes: Burley diffuse, Schlick-GGX specular with
  `V_GGX`, Schlick Fresnel with the engine's `f90`, and the multiple-scattering energy compensation
  `1 + f0 (1/E - 1)`. `E` comes from the engine's DFG look-up texture, which a shader cannot read;
  `tools/make_dfg_lut.py` recomputes it with the same Hammersley points and Smith-Schlick
  geometry term and stores it at the same texel centres as half floats (`textures/sd_dfg_lut.exr`,
  global `sd_dfg`). Two traps found by the parity test: the engine's `saturateHalf()` is not a
  [0, 1] clamp (only an FP16 cap), and a spatial shader without render modes gets *Lambert*
  diffuse - hence `render_mode diffuse_burley` in every variant. Area lights never reach
  `light()` (the engine shades them itself as long as the shader does not read the area
  built-ins). Not reproducible: the soft-light size term `A` (a few thousandths of N.L for lights
  with a size). Measured difference to the engine: 0.07 % at the 99th percentile.
- The self-shadow itself marches from the hit towards directional lights over the relief:
  hard (any relief above the ray) or contact-hardening (Tatarchuk 2006: the largest
  `(relief - ray) * k / distance`), with a 1 % bias, fading out towards `sd_shadow.y` metres.

### 3.3 Opt-in depth write

`DEPTH` at the hit makes props intersect the relief. Its costs: the material loses early-Z, and
its depth pre-pass must run the fragment shader - the variant writes `VERTEX = VERTEX;` so the
engine does not draw its pre-pass with the shared flat-depth material. With the pre-pass on, the
colour pass keeps a fragment only if its depth is EQUAL to the pre-pass depth, and the two passes
are separately compiled shaders: they disagreed in the last bit on 1.3 % of pixels, which showed
as holes. The written depth is therefore rounded to 12 mantissa bits (0.25 mm at 2 m); a value that
lands exactly on a rounding step can still disagree (0 to 13 per million pixels measured).

## 4. `DisplacementField3D`

### 4.1 Mesh and snapping

`L` rings of `N x N` quads (built once per (L, N) in `build_mesh`, cached while a field exists).
Ring 0 is a full square with spacing `s0`; ring `k` is a square annulus from `N/4` to `N/2` of its
own spacing `s0 * 2^k`. Per vertex: `UV` = integer lattice coordinates in units of `s0`, `UV2` =
(ring, seam flag). The mesh instance is moved to the camera snapped to multiples of `2^L * s0`,
so every ring's vertices always sit on the same world positions: nothing slides over the height
map when the camera moves (render test: zero height change near a walking camera).

### 4.2 Crack-free seams (geomorphing)

Towards its outer edge, ring `k` morphs: odd lattice vertices slide onto their lower even
neighbour (`lattice - odd * 2^k * m`, exact in lattice units) and the height is sampled one mip
coarser (`lod = log2(s0) + (k + m)`). At `m = 1` the ring's edge vertices have the same lattice
positions, the same LOD and therefore bit-identical heights as ring `k + 1`'s inner-edge vertices
at `m = 0`; the shared edges are identical and the rasterizer leaves no gaps. Edge vertices carry
flags that force `m = 1` (outer edge) and `m = 0` (inner edge). The morph ranges are chosen so
the distance-based morph agrees with the flags for every camera position inside a snap cell:
it ends before `R_k - delta` and starts after `sqrt(2) * (R_(k-1) + delta)` (`delta` = half the
snap); the logic tests check this for Epic's grid and a dense one, and the validator warns when a
custom resolution makes it impossible. Because the fine ring is fully morphed where the grid's
snapping moves ring boundaries, the geometry does not pop either (render test: under 1 mm per
1 cm camera step in the morph band). No skirts are needed.

### 4.3 Heights, layers, the ground

`y = ground + lift + fade_field(d) * fade_pom(d) * sum_i w_i * height_m_i * h_i(xz, lod)`

- `ground` and the layer weights `w` come from an `SDGroundBake` (or a flat plane at the node's
  height). The bake renders the ground group's meshes top-down in their own `World3D` with a
  capture shader that writes the world height as 16-bit fixed point split over two channels
  (exact in the half-float target), the layer index and coverage, and stores the captured image
  as it is: nothing runs per texel on the CPU (0.3 s for the demo's 90 x 90 m at 5 cm, most of it
  waiting for frames). `sd_ground.gdshaderinc`, shared by the field and the pebbles, decodes the
  4 x 4 texels around a point: a texel is displaceable when it and its four neighbours are
  covered and no neighbour differs by more than `step_limit` (0.8 x the texel size: slopes up to
  39 degrees are ground, kerbs and steps are not, whatever the texel size); uncovered texels take
  the mean height of the covered ones around them; heights, weights and the gradient normal are
  bilinear between texel centres; beyond the bake nothing is displaceable. `SDGroundBake.sample()`
  is the same function on the CPU, and a render test checks the field's vertices against it.
- The vertices pass the normalised layer weights to the fragments (varyings), so the fragments
  do not decode the bake again.
- The field is drawn *on top of* the original ground: relief "up only", the geometry raised by
  `lift` (2 mm).
  Where no layer is displaceable, vertices dive `push_down` under the ground and the ground mesh
  hides them - no `discard`, so early-Z stays.
- Collision stays on the original ground.

### 4.4 Why the fragments still march

The geometry can only carry relief down to its vertex spacing (4 cm at Epic; the denser grids
measured in 4.5 cost up to 2.2 ms more). A gravel's stones are smaller than
that, so the geometry alone shows soft lumps. Each field fragment therefore marches the full-resolution
relief over the whole slab along its true view ray, exactly like the ground material with
`height_center = 0`: the first hit of the ray with the height field does not depend on where the
proxy geometry was rasterized. The geometry adds what POM cannot: pixels the flat ground would
not cover (silhouettes), real depth for SSAO and for props, and the coarse relief. The relief is
measured from the ground, as the ground material measures it (`lift` raises only the proxy
geometry), so the field shades like the parallax ground it covers (render test: 0.15 % mean
difference inside the grid, 0.08 % in the last metre, zero beyond) and its edge is invisible.

The march's mip level and the texture gradients come from the footprint on the ground plane under
the proxy (the view ray's point at relief height 0), not from the proxy's own screen derivatives:
those jump at the proxy's bumps and silhouettes and would blur the relief there. A render test
checks the field's hits against the CPU ray tracer like the surfaces' (90th percentile 0.10 mm)
and its self-shadow against the CPU height-field shadow (99.8 %).

### 4.5 What the field costs, and why

In Forward+ the depth pre-pass runs a material's fragment shader when its vertex shader moves
the vertices (to get the normal-roughness buffer right), so the field's fragments march the relief
twice per frame, where the ground's POM runs once. Its triangles are small on screen (a few pixels,
thin at grazing angles), and the GPU shades 2 x 2 pixel quads, so part of that work is thrown away.
`tests/benchmark.gd --explore` measured the field on top of High's POM at 1080p on the GTX 1080:
1.4 ms for 3 rings of 96 quads at 4 cm, 1.5 ms for 4 x 96 at 4 cm, 1.9 ms for 3 x 128 at 3 cm,
2.1 ms for 4 x 160 at 2 cm and 3.6 ms for 4 x 256 at 1.5 cm. Epic therefore uses the 3 x 96 grid
at 4 cm: it lifts cobbles and rocks, and the parallax (identical on and off the field) carries the
gravel.

## 5. `PebbleScatter3D`

One `GPUParticles3D` whose particles are pebble slots in a window of cells that follows the camera
(Terrain3D's particle pattern, MIT). The particle shader places slot `i` of window cell `c` from a
hash of the cell's *world* coordinates and the slot, so pebbles stay put while the window moves
(render test: zero pixels change when the camera moves a metre). Density = layer weight x layer
density x preference for height-map valleys; pebbles rest on `max(relief, field proxy relief)` so
the proxy's depth never hides them; they shrink away between half the radius and the radius.
Rejected slots keep a zero transform instead of being deactivated: a deactivated particle is not
processed again until it is re-emitted and could not come back when the window moves.

## 6. `SurfaceDisplacement` and presets

`SDSettings.create_preset()` defines Off / Low / Medium / High / Epic; the node combines the
preset with four feature switches (a switch can remove a feature, never add one), writes the
globals, swaps the variants of every registered SD material at runtime (materials entering the
tree later are registered through `SceneTree.node_added`), and sets the fields' ring count,
resolution and spacing and the scatters' density and radius. In the editor it only writes the
globals, so saved materials keep their variant (editor check).

## 7. Resource lifetime

The field and scatter own their render objects as *internal* children (never saved, freed with
their parent); the field's static mesh cache is cleared when the last field leaves the tree; the
bake's capture viewport is freed after the capture. Shader globals hold plain values only. Every
test runner fails on "RID leaked", "ObjectDB instances leaked" or "resources still in use" at
exit.

## 8. How the tests avoid agreeing with themselves

- References are independent: a CPU ray / height-field intersection and a CPU height-field
  shadow written from the documented conventions, the height image's own mip data, analytic
  mesh heights, Godot's own lighting (the same material with the engine's `light_compute`), and
  ORMMaterial3D.
- Debug views write exact numbers (hit offset, world height, march cost, self-shadow factor) into
  a half-float viewport; the harness decodes them.
- Tests that check a direction use only the pixels where the right and the wrong answer differ
  (the shadow-edge test, the depth-write test), so a broken feature cannot pass on pixels that
  look the same either way.
- `tests/run_mutations.py` re-introduces known bugs one at a time (the list is in the README),
  each of which must turn its tests red.
